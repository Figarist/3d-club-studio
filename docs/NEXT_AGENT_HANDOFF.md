# Передача наступному агенту

## Знімок стану

Цей handoff підготовлено від чистого `main` на `6546bec`. Код застосунку
залишається на `3df6a40`: версія 1.9.0, `schemaVersion: 1`. Наступні коміти
документації можуть пересунути `HEAD`, не змінюючи кодові хеші доказів.
Каталог має 72 місії: 12 базових, 12 Adventure Pack і 48 нових моделей
одноколірного каталогу (20 рельєфів/корисних речей, 12 персонажів, 8 оптичних
відкриттів, 8 інженерних моделей).

Повний опис контрактів розширень і сумісності — у [EXTENSIONS.md](EXTENSIONS.md).
Завершений архітектурний аудит описує попередній baseline 1.8.1; це історія
знайдених і виправлених дефектів, а не список поточних задач.

## Де шукати код і власників стану

| Область | Власник і точка входу |
|---|---|
| Запуск і UI | `index.html` завантажує локальні IIFE у визначеному порядку, `src/app.js` останнім. `src/app.js` (`StudioApp`) збирає UI, параметри, транзакції, Undo/Redo, autosave, імпорт і вибір місії; розмітка та стилі — `index.html` і `styles.css`. |
| Ідентичність і каталог | `src/contentRegistry.js` задає сталі `missionKey`/`modelKey` і атомарну реєстрацію. `src/missionManager.js` володіє каталогом та активною місією; контент паків — у `src/content/`. Числові ID місій є сталими публічними ID і збережені для сумісності, включно з новими діапазонами 101–120, 151–170 та 201–208. |
| Файли проєкту | `src/projectState.js` валідовує та нормалізує JSON до застосування. Версія схеми окрема від версії застосунку; імпорт має зберігати сумісність і не змінювати поточний проєкт при помилці. |
| Генератори й контент | `src/generators/*` будують `THREE.Group`; Minecraft додатково володіє редагованою сіткою й палітрою. StudioApp читає DOM-контроли з кешу `_domCache` та передає `params` генераторам; поточні значення серіалізуються в `serializeState().controls`. Нові моделі: `src/content/funReliefs.js`, `funDiscoveries.js`, `funEngineering.js`; відповідна геометрія та генераторна поведінка — у `src/generators/`. |
| Сцена й демо | `src/sceneManager.js` володіє переданими групами, bounds, камерами, ефектами та Binary STL. `physicsMechanics.js` створює екранні дії/результати, `app.js` в'яже UI-кнопки, а короткочасні цілі й снаряди живуть у `SceneManager.effectsGroup`. Це навчальне демо, не фізична симуляція; ефекти не мають потрапляти в STL. |
| Інші окремі стани | `src/lessonCompanion.js` володіє станом викладача й таймером окремо від проєкту. `snapshotCompareController.js` зберігає V1/порівняння, `passportPrintController.js` створює паспорт/PNG; жоден із них не підтверджує друк. |

Проєкт залишається офлайн Vanilla JS/CSS + локальний Three.js r128, із
модулями IIFE на `window.*`. Дизайн моделей має починатися з геометрії,
читабельної в одному пластику: силует, рельєф, товщина та зв'язність важливіші
за колір, напис або просте масштабування. Одна одиниця сцени дорівнює 1 мм;
піксельна зв'язність і згенерований STL не доводять замкнену manifold-сітку.

## Поточні докази та межі

`verification/content-evidence/manifest.json` охоплює 101 скінченну
конфігурацію. Фінальний PASS є лише для 4/101: `funrelief_compass_treasure_map`,
`iron_mole`, `mountain_boat` і `ballista_bow`. Це 13 оригінальних JPEG із
фактичного UI та перевірені дії; **97 конфігурацій лишилися без фінального
перегляду** за прямою вказівкою власника зупинити повний прогін. Статус пакета —
`INCOMPLETE`. Маніфест закріплений за кодом `3df6a40`; його поточні source hashes
не треба оновлювати через суто документальні зміни. Якщо зміняться хешовані
файли застосунку, познач captures як докази для старого source revision. Не
переписуй хеші й не оголошуй їх актуальними без нового захвату в межах окремо
визначеного bounded-пакета.

Див. [FUN_CONTENT_REVIEW.md](FUN_CONTENT_REVIEW.md) для точних результатів.
Описані там schema/registry/state/export checks і браузерний захват — попередні
запуски; вони не запускалися в цьому документаційному оновленні. Імпорт та
відновлення проєкту через реальний file chooser були перевірені. Очікують на
перевірку повний візуальний каталог, 12 фактичних UI-взаємодій, сумісність UI на
1024×768 і readback саме файла, завантаженого через Save/export. Також не
перевірені запуск через `file://`, слайсер/manifold та фізичний друк. Дитяче
сприйняття й довговічність деталей — `Not verified`.

Не перебудовуй `manifest.json`, `coverage.json`, `gallery.html`, `capture.json`,
`review.json` чи зображення для документаційної задачі. Новий source hash
потребує реального захвату проти відповідного коду; наявні 13 оригіналів не можна
представляти як 101 перевірений результат.

`prepare-content-evidence.cjs` може перенести старий `review.json` зі статусом
PASS у новий маніфест: сам генератор галереї не анулює його автоматично за
зміненою геометрією. Перевіряй відповідність capture/source hashes окремо;
`coverage.json` є знімком звіту, а не постійним монітором актуальності.

## Наступні пріоритети

1. **UI/UX:** обери одну підтверджену проблему в основному робочому процесі й
   перевір її на фактичних розмірах 1366×768 та 1024×768. Ідеї у
   `UI_UX_UPGRADE_PROMPT.md` і `MASTER_CLEANUP_UX_UI_PROMPT.md` — історичні
   пропозиції, не список із 15 обов'язкових змін і не запит на повний рефакторинг.
2. **Візуальний перегляд 97 конфігурацій:** повний прогін раніше зупинив власник.
   Не поновлюй його автоматично. Новий явний запит людини може визначити новий
   обсяг; тоді бери лише чітко вибраний bounded-пакет, переглядай реальні види й
   дії та записуй окремий verdict.
3. **Пресети й функції:** додавай їх, коли вони дають дитині помітну дію або
   вибір із різними формами, історією чи навчальним результатом. Дотримуйся
   stable keys, атомарної реєстрації, mono-first перевірки й extension-рецепта;
   не запускай автоматично вже виконаний 48-модельний пакет із
   `FUN_CONTENT_UPGRADE_PROMPT.md`. Новий явний запит людини може задати інший обсяг.

## Обмежені перевірки

Дотримуйся власницького бюджету: одна сфокусована партія — до 20 знайдених
тестових випадків і 60 секунд; для невеликого виправлення — до 180 секунд загалом.
Запускай лише перевірки, потрібні зміненій поведінці. UI треба перевіряти
справжнім натисканням/введенням і результативним станом, а не прямим викликом
callback чи підміною preferences.

| Ситуація | Обмежена команда або процедура |
|---|---|
| Документи | `rtk git diff --check`; перевір посилання на файли в змінених документах. |
| Контракти реєстру | `rtk proxy node verification/verify-content-registry.cjs` — малі набори та атомарна реєстрація. |
| Схема/імпорт | `rtk proxy node verification/verify-project-state.cjs` — 15 випадків, тільки якщо змінювалася валідація стану. |
| Нові конфігурації | `rtk proxy node verification/verify-fun-state.cjs 0 20` — рівно до 20 конфігурацій; інші партії запускати лише за потреби. |
| STL-геометрія | `rtk proxy node verification/verify-fun-export.cjs` — чотири репрезентативні експорти, без доказу реального завантаження, слайсингу чи друку. |
| CUA захват | `rtk proxy node --check verification/capture-content-ui.mjs` перевіряє лише синтаксис. Сам helper не є standalone-runner: у CUA з реальним локальним UI викликай експортований `captureRow(tab, cap, row, emitImage)` лише для вибраного рядка; потім відкрий оригінали й зроби окремий ручний review. |

`verify-content-evidence.cjs` — суворий gate завершеного візуального пакета; за
поточних 97 pending його не можна подавати як успішний і немає сенсу запускати
для звичайної зміни. Повні/довгі набори не запускати за замовчуванням.

## Межа завершення

Для кожної зміни запиши, що змінилося і чим саме це перевірено; позначай окремо
джерельні, детерміновані, браузерні, CI, live/device та фізичні докази. Для
версії документаційне редагування не вимагає bump. При кодовій зміні дотримуйся
`AGENTS.md`, staging тільки явних власних шляхів і процесу коміту/пушу, який
веде головний агент. Не закривай візуальну чи фізичну приймальну перевірку без
відповідних оригінальних доказів.
